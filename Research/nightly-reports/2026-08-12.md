`E.E1` has received **0.0012247 in total for one story.** Both entries render on the live page, one
directly above the other — today's in "5 applications on 2026-08-12", yesterday's as the first row
of "earlier — 35 applications from 2026-08-04 to 2026-08-11".

Two things are true and they point opposite ways:

- **The r2 damping worked in the right direction.** The repeat landed at 56% of the original
  (`spread` fell to 0.7071, `k` rose to 7.208). This is the reverse of the 08-10 observation, where
  `spread` could make a repeat land *harder* than its original. That specific failure mode did not
  recur tonight.
- **It was not collapsed, and could not have been.** `collapsed: 0` for the seventh consecutive
  night. `resolve_incidents()` works within one night's batch, and incident identity is derived from
  the driver text, so a re-summarised story two nights running is two incidents.

**On the obvious fix — it is not as obvious as it looks.** The two records share a byte-identical
primary URL, which invites a URL-overlap test. r2 measured that exact idea and rejected it: one AISN
newsletter issue is cited by five unrelated events, and linking on shared URLs chained **28**
developments into a single incident. What is different here is narrower — not a URL appearing
anywhere in two citation lists, but the *same first-listed source* on two records that also score
high on IDF-weighted text similarity. That is a candidate worth measuring against the trunk, not an
established fix, and the r2 finding is the reason to measure it before believing it.

No change made; recording the evidence.

### 5c. The day-over-day drift reference was re-stamped outside the chain

The audit printed `DRIFT vs 2026-08-12` — today's date — while the values it compared against
(`target_pct 81.5`, `review.pct 10.819`, `grounded_direct 1324`) are **yesterday's**. Confirmed:
`HEAD~1:Research/modeling/baselines.json` carries `last_run.date = 2026-08-11` with exactly those
checks. So `baselines.json` in the working tree was written by something between yesterday's commit
and this run, re-stamping `last_run.date` to today while leaving yesterday's `checks` in place.
Yesterday's report records the same pattern (an audit run at 01:46).

**Today this was harmless** — the compared values were still the right ones, so the drift lines are
correct and the gate result stands. The hole is structural: `audit_all.py` writes
`bj["last_run"] = {"date": TODAY, "checks": results}` unconditionally on every PASS, so any bare
`python3 audit_all.py` run before the nightly emit overwrites the reference with pre-emit numbers
stamped today. That is precisely the erosion detector added 2026-08-03, and it can be silently
reset — hiding up to one day of erosion — by a run that was only meant to look.

Worth a fix: either write `last_run` only when the run is the publishing one, or carry provenance on
it so the header can say what it actually compared.

### 5d. The T7 witness rows show the wrong sentence

`witness-statelaw.json` stores `"text": ev["text"][:180]` — the **first 180 characters of the
event**, not the sentence that produced the row. Three of the eight rows therefore read as
misattributed:

- `Idaho|y2026` displays an NCSL aggregate about 43 states
- `Montana|y2026` displays a report on nine states *considering* preemption bills
- `Nebraska|#525` displays a New York State Senate vote

**All three are correct.** Read against the matched context, the proximity rule bound each verb to
the right actor: *"Idaho enacted a law requiring chatbots to refer suicidal users to crisis
centers"*, *"Montana enacted a Right to Compute"*, *"separately, Nebraska enacted LB 525"*. The
extractor is sound; the display field is not. This is cosmetic in effect and corrosive in practice —
it makes a witness built to be audited look broken to anyone auditing it. The fix is to store the
matched window instead of the event head.

Atlas-side code, not wiki content, so no queue file. The gate passed, so nothing was filed to
`Wiki/_meta/queue/` tonight.
